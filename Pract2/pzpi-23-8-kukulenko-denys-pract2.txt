3 ОПИС ВИКОНАНОЇ РОБОТИ 
3.1 Загальні відомості про систему Назва системи: Spotify. 
Розробник: Spotify AB. 
Spotify — це одна з найбільших у світі платформ для потокового відтворення музики та подкастів, розроблена компанією Spotify AB. Система надає користувачам можливість слухати музичний контент у режимі онлайн, створювати власні плейлисти, отримувати персоналізовані рекомендації та взаємодіяти з іншими користувачами. Станом на сьогодні Spotify обслуговує сотні мільйонів користувачів по всьому світу, що робить її високонавантаженою розподіленою системою.

Основними функціями системи є:
•	реєстрація та авторизація користувачів;
•	пошук музики та виконавців;
•	створення та управління плейлистами;
•	рекомендаційні алгоритми на основі штучного інтелекту;
•	потокове відтворення аудіо;
•	збереження контенту для офлайн-доступу.

3.2 Архітектурний стиль системи 
Архітектура Spotify базується на мікросервісному підході у поєднанні з подієво-орієнтованою (event-driven) архітектурою. Перехід до мікросервісів був обумовлений необхідністю масштабування системи, підвищення її відмовостійкості та забезпечення незалежної розробки окремих компонентів. Кожен мікросервіс відповідає за конкретну бізнес-функцію і може розгортатися незалежно від інших. Подієво-орієнтований підхід дозволяє компонентам системи взаємодіяти через асинхронні повідомлення (події), що значно зменшує зв’язність між сервісами та підвищує гнучкість системи.
 Також варто зазначити, що Spotify використовує власну організаційну модель розробки (Squad/Tribe), яка безпосередньо впливає на архітектуру системи та її масштабованість. 
 
3.3 Основні компоненти системи Опис підсистем: 
-	Інтерфейс користувача: Клієнтські додатки для різних платформ, включаючи iOS, Android, десктопні операційні системи та веб-браузери. Інтерфейс адаптується під конкретний тип пристрою та забезпечує зручний доступ до функцій системи, таких як пошук музики, відтворення треків, управління плейлистами та взаємодія з рекомендаціями. 
-	Серверна частина: API Gateway, який виступає єдиною точкою входу в систему, приймає всі вхідні запити від клієнтів, виконує їхню автентифікацію та маршрутизацію до відповідних мікросервісів. 
-	Рівень бізнес-логіки: Сукупність незалежних мікросервісів, що реалізують основні функції системи. До них належать сервіс авторизації, сервіс користувачів, сервіс плейлистів, сервіс рекомендацій, сервіс пошуку та сервіс стрімінгу аудіо. Кожен сервіс виконує окрему бізнес-функцію та може масштабуватися незалежно від інших. 
-	Рівень зберігання даних: Використовуються різні типи баз даних залежно від специфіки задач. Cassandra застосовується для роботи з великими обсягами даних та високою швидкістю запису, PostgreSQL — для транзакційних операцій, а Redis — для кешування та швидкого доступу до часто використовуваних даних. 
-	Допоміжні сервіси: До допоміжних компонентів належать мережа доставки контенту (CDN), яка забезпечує швидке потокове відтворення аудіо, системи обміну повідомленнями для реалізації подієво-орієнтованої взаємодії між сервісами, а також інструменти моніторингу та забезпечення надійності системи. 
 
3.4 Взаємодія компонентів 
Клієнтський пристрій (мобільний додаток, веб або десктоп) відправляє запит до балансувальника навантаження, який розподіляє трафік між доступними серверами. Далі запит передається до API Gateway, який виконує маршрутизацію до відповідного мікросервісу. API Gateway може звертатися до системи сервіс-дискавері або внутрішнього реєстру сервісів для визначення адреси потрібного мікросервісу (наприклад, сервісу рекомендацій або пошуку). Мікросервіс обробляє запит, взаємодіючи з кешем (Redis) або базою даних (Cassandra, PostgreSQL), після чого повертає відповідь у форматі JSON клієнту. У випадку відтворення музики, після отримання метаданих (інформації про трек), запит на аудіофайл не проходить через основні сервери, а направляється безпосередньо до найближчого сервера CDN. Це дозволяє забезпечити швидке та стабільне потокове відтворення. 
 
 
Рисунок 1.1 – Діаграма послідовності взаємодії користувача з системою Spotify 
 
Діаграма ілюструє покроковий процес взаємодії користувача з системою. Вона демонструє чітке розділення відповідальності: легкі запити (авторизація, пошук, отримання даних) обробляються через API Gateway та мікросервіси, тоді як передача аудіоконтенту здійснюється через CDN, що значно зменшує навантаження на серверну частину системи. 
 

 Рисунок 1.2 – Діаграма компонентів Spotify  
 
Діаграма відображає загальну структурну організацію системи Spotify.
Показано єдину точку входу до системи — API Gateway, через який проходять усі запити клієнтів. Також відображено використання механізмів сервіс-дискавері для динамічної маршрутизації запитів між мікросервісами. Архітектура реалізує підхід «Polyglot Persistence», при якому різні мікросервіси використовують різні типи баз даних залежно від своїх задач: Cassandra застосовується для масштабованого зберігання даних, PostgreSQL — для транзакційних операцій, а Redis — для кешування. Окремо виділено CDN, яка використовується для доставки аудіоконтенту безпосередньо користувачу, що дозволяє уникнути перевантаження основної серверної інфраструктури. 
 
3.5 Масштабованість та надійність 
Spotify є високонавантаженою системою, тому особлива увага приділяється її масштабованості та надійності. Масштабування досягається за рахунок використання контейнеризації (Docker) та оркестрації (Kubernetes), що дозволяє автоматично збільшувати кількість екземплярів сервісів при зростанні навантаження. 
 Для забезпечення відмовостійкості використовуються такі підходи:
•	балансування навантаження між серверами;
•	використання патерну Circuit Breaker для запобігання каскадним збоям;
•	механізми повторних спроб (Retry);
•	резервування та реплікація даних.
Кешування відіграє важливу роль у підвищенні продуктивності системи. Дані, які часто використовуються, зберігаються в Redis, що дозволяє значно скоротити час відповіді.

3.6 Приклади програмної реалізації 
Для наочної демонстрації принципів мікросервісної архітектури та механізмів забезпечення відмовостійкості було розроблено навчальний програмний приклад. Основна увага приділялася патерну Circuit Breaker (Запобіжник), який є важливим елементом у розподілених системах, подібних до Spotify, для запобігання каскадним збоям між мікросервісами. 
 
Запит до ШІ: " Згенеруй базовий приклад того, як працює API Gateway у поєднанні з Circuit Breaker (на прикладі Node.js або Java), який би демонстрував ізоляцію збоїв мікросервісу рекомендацій у музичному стрімінговому сервісі (аналог Spotify)". 
 
1.	const express = require('express');
2.	const axios = require('axios');

3.	const app = express();

4.	app.get('/music/:userId', async (req, res) => {
5.	try {
6.	const response = await axios.get(`http://recommendation-service/${req.params.userId}`);
7.	res.json(response.data);
8.	} catch (error) {
9.	res.json({
a.	fallback: true,
b.	data: ["Популярний трек 1", "Популярний трек 2"]
10.	});
11.	}
12.	});

13.	app.listen(3000, () => console.log("Service running")); 

Наведений програмний код реалізує простий мікросервіс, який здійснює мережевий виклик до зовнішнього сервісу рекомендацій для отримання списку музичних треків користувача. Запит виконується за допомогою HTTP-клієнта axios у межах обробника маршруту /music/:userId. У разі успішного виконання запиту (рядок 7) сервіс отримує відповідь від мікросервісу рекомендацій та повертає її клієнту у форматі JSON (рядок 8). Таким чином забезпечується стандартна взаємодія між компонентами мікросервісної архітектури. Однак у випадку недоступності сервісу рекомендацій або виникнення помилки під час виконання запиту (наприклад, перевищення часу очікування або відсутність з’єднання), керування переходить до блоку catch (рядок 9). У цьому блоці реалізовано спрощений аналог патерну Circuit Breaker. Замість того, щоб повернути клієнту помилку та порушити роботу сервісу, система повертає заздалегідь визначений резервний результат (fallback), який містить список популярних треків (рядки 10–13). Це дозволяє уникнути повної недоступності функціоналу та забезпечити безперервність роботи сервісу.

Таким чином, наведений код демонструє принцип «елегантної деградації» (graceful degradation), при якому система Spotify може продовжувати часткову роботу навіть у випадку збоїв окремих компонентів. Наприклад, замість персоналізованих рекомендацій користувач отримує базовий список популярних треків. Хоча у даному прикладі використано спрощену реалізацію без повноцінної бібліотеки Circuit Breaker, логіка обробки помилок і fallback-поведінка відповідають основній ідеї цього патерну — ізоляції збоїв та запобіганню їх поширенню на інші частини системи.

4 ВИСНОВКИ 
У результаті виконання практичного заняття було досліджено архітектуру сучасної програмної системи Spotify, яка є однією з найбільших платформ потокового відтворення музичного контенту. У ході роботи було визначено, що система побудована на основі мікросервісного архітектурного стилю у поєднанні з подієво-орієнтованим підходом. Така архітектура забезпечує гнучкість, масштабованість та можливість незалежного розвитку окремих компонентів системи. Було проаналізовано основні підсистеми Spotify, включаючи клієнтський рівень, API Gateway, рівень бізнес-логіки, систему зберігання даних та допоміжні сервіси. Окрему увагу приділено механізмам взаємодії між компонентами, зокрема використанню CDN для ефективної доставки аудіоконтенту та зменшення навантаження на серверну інфраструктуру. Також було розглянуто підходи до забезпечення надійності системи, такі як балансування навантаження, кешування та обробка помилок. На практичному прикладі програмного коду продемонстровано реалізацію механізму обробки збоїв (аналог патерну Circuit Breaker), що дозволяє системі зберігати працездатність навіть у випадку недоступності окремих сервісів. Отримані результати дозволили закріпити теоретичні знання з архітектури програмного забезпечення та сформувати практичні навички аналізу складних розподілених систем. Виконання роботи сприяло глибшому розумінню принципів побудови сучасних високонавантажених сервісів та підходів до забезпечення їх ефективності і надійності.
